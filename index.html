1. Princípios de Implementação de Sistemas Distribuídos

Ideia central: dividir tarefas entre várias máquinas que se comunicam pela rede para resolver problemas maiores de forma eficiente, escalável e tolerante a falhas (bancos, redes sociais, jogos online, nuvem, e-commerce).

Programação Paralela

Divide tarefas dentro do mesmo computador: multithreading, GPU, multicore.

Programação Distribuída

Amplia para múltiplos computadores conectados em rede.

Objetivos de um Sistema Distribuído

ObjetivoO que significa
TransparênciaLocalização (não preciso saber onde está o recurso) · Replicação (não preciso saber que há cópias) · Acesso (forma uniforme de acessar) · Concorrência (vários usuários sem conflito)
EscalabilidadeSuportar crescimento de usuários/dados, evitar gargalos centralizados, facilitar manutenção (serviços separados)
Tolerância a falhasSe uma máquina cai, o sistema continua. Redundância e recuperação
DesempenhoBaixa latência (resposta rápida) e alto throughput (muitas requisições/segundo)

Princípios fundamentais de implementação

  • Comunicação entre processos: Sockets (baixo nível, mensagens binárias) · RPC (função remota como se fosse local) · Mensageria (Kafka, RabbitMQ – assíncrona).
  • Sincronização: relógios lógicos (Lamport) e controle de concorrência (exclusão mútua distribuída, locks distribuídos – ZooKeeper).
  • Consistência e replicação: forte (sempre iguais) × eventual (ficam iguais com o tempo). Teorema CAP: Consistência × Disponibilidade × Tolerância a Partições → escolhe 2.
  • Gerenciamento de falhas: detecção (heartbeats, timeouts) e recuperação (checkpoint, rollback, replicação).
  • Escalabilidade: balanceamento de carga · sharding (dividir dados entre servidores) · elasticidade (adicionar/remover máquinas sob demanda).

Do monólito aos microsserviços

Monólito em camadas

  • Domínio/Modelo: entidades (Cliente, Pedido, Produto) e suas validações
  • Negócio/Serviço: regras (calcular desconto, verificar crédito)
  • Dados/Repository: acesso ao banco (salvar Pedido no PostgreSQL)
  • Apresentação/API: contato com usuário/sistema (API REST, tela)

Microsserviços (e-commerce)

  • Catálogo: produtos, banco próprio (MongoDB)
  • Pedidos: regras de compra, consulta o Catálogo (PostgreSQL)
  • Pagamentos: transações, gateways (PayPal, Stripe)
  • Usuários: cadastro, login, preferências

Comunicação: síncrona via REST/gRPC; assíncrona via fila (Pedidos publica evento → Pagamentos consome).
Benefícios: escalabilidade (só mais instâncias de Pedidos), independência tecnológica, resiliência (Pagamentos cai, o resto funciona), evolução mais rápida.

⚠️ Pegadinha: “serviços separados que se comunicam pela rede” = distribuída, não “paralela”.

2. Threads na prática: Concorrência, Paralelismo e Async/Await

Concorrência

Lidar com várias tarefas “ao mesmo tempo”, mas não necessariamente no mesmo instante. As tarefas são intercaladas (o processador alterna). Ideal quando há esperas: disco, rede, usuário.

Paralelismo

Execução de várias tarefas no mesmo instante em núcleos/processadores diferentes. Requer multicore. Ideal para tarefas pesadas de CPU: cálculos, renderização.
⚠️ “Execução simultânea em múltiplos núcleos” = paralelismo. “Execução intercalada em uma ou mais threads” = concorrência.

Thread × Processo

Thread: menor unidade de execução dentro de um processo; compartilha memória e recursos com as outras threads.
Processo: tem espaço de memória próprio e isolado → criar, gerenciar e comunicar processos custa mais ao SO → mais pesado.

Thread bloqueada

Thread ociosa esperando uma operação terminar. Não pode fazer mais nada, mesmo com a CPU livre.

Thread.Sleep(1000);                        // para literalmente 1s
File.ReadAllText(path);                    // espera o disco
httpClient.GetStringAsync(url).Result;     // espera a rede de forma BLOQUEANTE

Problemas: baixo aproveitamento de recursos · menor escalabilidade (cada requisição prende uma thread) · UI congelada · servidor esgota o pool de threads.

Abordagem do C#: TPL (System.Threading.Tasks)

  • Task = operação que pode rodar de forma assíncrona; Task<T> = retorna um resultado.
  • async marca o método; await pausa o método até a tarefa terminar, sem bloquear a thread.
  • O runtime usa um thread pool eficiente (evita criar threads demais).

Como funciona por baixo dos panos

  1. O compilador transforma o método async em uma máquina de estado; cada await é um ponto de suspensão.
  2. O await registra uma continuação e devolve o controle imediatamente → a thread fica livre.
  3. Quando a tarefa termina, a continuação roda — geralmente no mesmo contexto, a menos que se use ConfigureAwait(false).
  4. try/catch funciona normalmente; métodos async devem retornar Task/Task<T>.
public async Task<string> BuscarAsync()   // ✅ assinatura correta
{
    await Task.Delay(2000);                // ✅ não bloqueia (≠ Thread.Sleep)
    return "ok";
}

// Disparar várias e aguardar TODAS:
var t1 = EnviarPixAsync(a); var t2 = EnviarPixAsync(b); var t3 = EnviarPixAsync(c);
await Task.WhenAll(t1, t2, t3);   // tempo ≈ a mais lenta
// Task.WhenAny(...) → retorna quando a PRIMEIRA terminar

Motivações para usar async/await

  1. Evitar bloqueio – await Task.Delay libera a thread (concorrência cooperativa).
  2. Melhor uso de recursos – milhares de tarefas sem milhares de threads.
  3. Código simples – parece sequencial, mas é assíncrono.
  4. Composição – Task.WhenAll, Task.WhenAny.
  5. Escalabilidade – APIs e microsserviços atendem mais usuários com menos recursos.
  6. Banco de dados – EF / Dapper com await: app não trava esperando o banco.
  7. PIX – várias transações simultâneas; o sistema continua operando enquanto aguarda as APIs externas.
⚠️ Async não torna a operação mais rápida e não elimina threads. A vantagem é não bloquear a thread durante a espera.
⚠️ async void só para event handlers. Task.Sleep não existe. await Thread.Sleep não compila.

Protocolos

Confiável, orientado a conexão, garante ordem e entrega. Base de HTTP e RPC.

UDP

Mais rápido, não garante entrega/ordem. Jogos online, streaming (baixa latência).
  • HTTP/HTTPS: base dos serviços web e REST. Simples e interoperável.
  • gRPC: RPC moderno sobre HTTP/2 + Protobuf. Rápido e multiplataforma.

Ferramentas

  • Sockets TCP/UDP – ponto a ponto, baixo nível.
  • RPC/RMI – Java RMI (ensino), gRPC (mercado), WCF (.NET corporativo).
  • APIs REST – sobre HTTP; Postman, Swagger/OpenAPI.
  • Message brokers – RabbitMQ (filas, ordem e entrega garantida) · Kafka (eventos em larga escala) · MQTT (IoT).
  • Coordenação – ZooKeeper (clusters), etcd (configuração no Kubernetes).
  • Alto nível – Hadoop/Spark, Akka (atores), Kubernetes, AWS SQS, Azure Service Bus, Google Pub/Sub.

Middleware

Camada intermediária que facilita a comunicação, abstrai protocolos e oferece serviços (autenticação, mensageria, transações).

API

O contrato: conjunto de regras e interfaces para acessar funcionalidades de um software.

Problemas clássicos

  • Deadlock: dois ou mais processos bloqueados indefinidamente, cada um esperando um recurso que o outro segura (espera circular).
  • while(true) sem saída: loop infinito, consome CPU continuamente e impede outras tarefas.
  • C++ new sem delete: memory leak – memória continua alocada; a thread segue, mas o sistema perde eficiência até travar.
  • Garbage Collector (C#, Java): gerencia memória automaticamente, evitando vazamentos em ambientes multithread.
  • Alto desempenho: minimizar latência entre nós e otimizar recursos, evitando gargalos.

5. Semáforos e Mutexes

Várias threads + recursos compartilhados (memória, arquivos, dispositivos) sem sincronização = race conditions, dados corrompidos, comportamento indefinido.

  • Concorrência: várias unidades de execução progredindo ao mesmo tempo.
  • Sincronização: coordenar o acesso correto aos recursos.
  • Exclusão mútua: só uma unidade na região crítica por vez.

🔒 Mutex

Acesso exclusivo: só 1 thread/processo possui por vez.
Local (intra-processo) ou nomeado (inter-processo).
Usar quando a operação deve ser atômica.
Ex.: lista ligada não thread-safe, escrita em arquivo, hardware exclusivo.

🚦 Semáforo

Contador de acessos simultâneos permitidos.
Binário (0/1) = mutex · Contável = até N.
Usar para limitar concorrência ou sinalizar produtor/consumidor.
Ex.: limitar 10 conexões, pool de conexões DB, buffer limitado.

Sincronização × Sinalização

Sincronização = coordenar acesso a recursos (mutex, semáforo). Sinalização = comunicar eventos entre threads (ManualResetEvent, AutoResetEvent, condition variables).

Armadilhas

  • Deadlock – espera circular entre locks.
  • Starvation – uma thread nunca obtém o lock.
  • Priority inversion – thread de baixa prioridade segura recurso da de alta.
  • Segurar lock por muito tempo – reduz a concorrência.

Boas práticas

Regiões críticas curtas · preferir coleções thread-safe (ConcurrentQueue, ConcurrentDictionary) · não bloquear em I/O longo · usar timeouts e tratar exceções.

APIs de sincronização em C#

lock(obj) (açúcar para Monitor) · Monitor.Enter/Exit/TryEnter · Mutex · Semaphore / SemaphoreSlim (Slim: intra-processo, mais rápido) · ReaderWriterLockSlim (muitos leitores, um escritor).

private readonly object _bloqueioSaldo = new object();   // objeto privado e dedicado

public void Sacar(decimal valor)
{
    lock (_bloqueioSaldo)            // só 1 thread por vez aqui dentro
    {
        if (saldo >= valor) saldo -= valor;
    }                                // liberado automaticamente, mesmo com exceção
}

Como o lock funciona: (1) objeto de bloqueio privado; (2) quem entra adquire acesso exclusivo, os outros esperam; (3) liberação automática mesmo com exceção; (4) atualizações ficam sequenciais e seguras. A thread que já tem o lock pode readquiri-lo (reentrante).

Semaphore/SemaphoreSlim: se a contagem é zero, a thread bloqueia; quando alguém chama Release(), uma bloqueada entra.

6. Monitor – Enter | Exit | TryEnter

Classe de System.Threading que permite que apenas uma thread por vez execute uma seção crítica, quando todas usam o mesmo objeto de bloqueio. Analogia: uma chave – uma pessoa entra, altera o estoque e devolve a chave.

Problema que resolve: race condition. Estoque = 10, duas threads vendem 7 ao mesmo tempo: ambas leem 10 antes de atualizar → vendem 14 itens. Com Monitor, a 2ª só lê depois da 1ª terminar (vê 3 e recusa). Ver no laboratório →

Onde usar: estoque, contas bancárias, sistemas de pedidos, filas/listas compartilhadas, qualquer objeto acessado por várias threads.

MétodoResponsabilidade
Monitor.Enter(bloqueio)Adquire o bloqueio; se outra thread tem, espera
Monitor.Exit(bloqueio)Libera o bloqueio da thread atual
bool ok = Monitor.TryEnter(bloqueio, 100)Tenta adquirir por até 100 ms; retorna bool
if (Monitor.TryEnter(_bloqueio, 100))
{
    try   { /* região protegida */ }
    finally { Monitor.Exit(_bloqueio); }   // SEMPRE no finally
}
else
{
    // não conseguiu em 100 ms → segue outro caminho
}

Exemplo que ajuda a diferenciar (API que consulta serviço externo)

  • lock: atualização rápida de um contador compartilhado.
  • Monitor: tenta o bloqueio por 100 ms e segue outro caminho se não conseguir.
  • Semaphore(3): no máximo 3 acessos simultâneos ao recurso.
  • SemaphoreSlim(3): no máximo 3 operações assíncronas com WaitAsync.
  • Mutex nomeado: impede duas instâncias do programa de executarem a mesma tarefa.

7. ManualResetEvent | AutoResetEvent

Problema: como uma thread avisa outra? Thread A (produtora) inicializa algo; Thread B (consumidora) não pode seguir antes. Como bloquear B sem ficar consultando uma variável em loop? → mecanismo de sinalização.

  • Dois estados: sinalizado (signaled) e não sinalizado (non-signaled).
  • WaitOne() aguarda · Set() sinaliza · Reset() volta a não sinalizado.
  • A diferença é o que acontece depois que uma espera é liberada.

🚪 ManualResetEvent — “portão”

Set() libera TODAS as threads aguardando. Continua aberto (novos WaitOne passam direto) até alguém chamar Reset().

Uso: “a inicialização terminou, todos podem começar”.
Risco: esquecer o Reset() e deixar todos passarem.

🎫 AutoResetEvent — “catraca”

Set() libera UMA thread e o evento volta sozinho a não sinalizado.

Uso: “chegou uma unidade de trabalho; um consumidor pode seguir”.
Risco: esperar vários sinais sem perceber como eles se acumulam/são consumidos (o estado é um só: vários Set() seguidos sem ninguém esperando valem como um sinal).
using var pronto = new ManualResetEvent(false);      // false = começa fechado
var w1 = Task.Run(() => { pronto.WaitOne(); Console.WriteLine("Worker 1 continuou"); });
var w2 = Task.Run(() => { pronto.WaitOne(); Console.WriteLine("Worker 2 continuou"); });
Thread.Sleep(1000);                                  // simula inicialização
pronto.Set();                                        // libera os DOIS
await Task.WhenAll(w1, w2);

using var sinal = new AutoResetEvent(false);
var consumidor = Task.Run(() => { sinal.WaitOne(); Console.WriteLine("Recebi o sinal"); });
sinal.Set();                                         // libera UM e fecha sozinho
await consumidor;

Reset() manualNecessário para bloquear de novoNão é necessário
Uso típicoAvisar que a inicialização terminouEntregar um sinal/trabalho a um consumidor
RiscoEsquecer Reset()Contar sinais errado

Aplicações: inicialização de serviço · testes concorrentes (largada simultânea) · produtor/consumidor · encerramento coordenado · pausar/retomar workers · aguardar recurso pronto.

Como escolher? “Quantas threads devem avançar quando o sinal chegar?” Várias → Manual. Uma por sinal → Auto.

💡 Regra prática: não bloqueie uma thread à toa quando pode aguardar uma Task assincronamente. Para filas reais, Channel<T> é melhor. Eventos sinalizam; para proteger dados use exclusão mútua (lock/Mutex).

⏱️ Síncrono vs Assíncrono (Task.WhenAll)

Três chamadas de API (PIX) que demoram 1s, 2s e 3s.

// Síncrono: total = 1 + 2 + 3 = 6s
await PixAsync(1); await PixAsync(2); await PixAsync(3);

// Concorrente: total ≈ 3s (a mais lenta)
await Task.WhenAll(PixAsync(1), PixAsync(2), PixAsync(3));
